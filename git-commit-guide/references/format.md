# 提交信息格式结构

## 标准格式（Conventional Commits）

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 各部分说明

| 部分 | 必填 | 说明 | 示例 |
|------|:--:|------|------|
| **type** | 是 | 提交类型，固定关键词 | `feat`, `fix`, `docs` |
| **scope** | 否 | 影响范围，模块/组件名 | `auth`, `api`, `ui` |
| **subject** | 是 | 简短描述，一行概括 | "添加用户登录功能" |
| **body** | 否 | 详细说明，解释 **为什么** 和 **做了什么** | 多行段落 |
| **footer** | 否 | 关联 issue、破坏性变更声明 | `Closes #123` |

## 格式约束

### subject 行规则
- 长度不超过 **50 字符**（中文约 25 字）
- 使用祈使句（"添加" 而非 "添加了" 或 "已添加"）
- 英文首字母小写，不加句号
- 中文不加句号
- 以空行分隔 subject 和 body

### body 规则
- 每行不超过 **72 字符**
- 解释 **做了什么** 和 **为什么**，不解释 **怎么做的**（代码自解释）
- 和 subject 之间空一行

### footer 规则
- 引用 issue：`Closes #123`、`Refs #456`
- 破坏性变更：以 `BREAKING CHANGE:` 开头，描述影响范围

## 示例

### 简单提交
```
feat(auth): 添加 JWT 登录验证
```

### 完整提交（含 body 和 footer）
```
fix(api): 修复分页参数越界导致的 500 错误

当 page 参数传入负数时，后端直接查询数据库导致异常。
现在在前端参数校验层增加了非负检查。

Closes #334
```

### 破坏性变更
```
refactor(db): 迁移用户表主键从 int 到 uuid

BREAKING CHANGE: user 表所有外键关联需要同步更新。
旧版 API 不再兼容整数 ID 格式。
```

## 常见反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| `fixed bug` | 用过去式 | `fix: 修复...` |
| `update code` | 太模糊 | `refactor: 提取公共校验函数` |
| `feat: 新功能` | 描述无意义 | `feat(search): 支持模糊搜索` |
| 一行超长全挤 subject | 不可读 | 拆分为 subject + body |
